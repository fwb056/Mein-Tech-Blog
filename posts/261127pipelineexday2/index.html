[Data Engineering] 로컬 Docker로 실시간 CDC 파이프라인 구축하기 (2일 차: Kafka → ClickHouse 실시간 적재 및 정합성 처리)

2026-11-26

1. 들어가며: Sink 커넥터 없이 ClickHouse 연결하기

1일 차에는 운영 DB(PostgreSQL)의 변경 로그(WAL)를 Debezium으로 캡처해 Kafka 토픽(dbserver1.public.orders)까지 스트리밍하는 구간을 완성했다.

2일 차에는 Kafka 토픽에 적재된 JSON 이벤트를 최종 목적지인 열 지향 DB(ClickHouse)로 실시간 적재한다. 일반적으로는 Kafka Connect에 별도의 Sink 커넥터 플러그인을 설치하지만, ClickHouse는 자체적으로 Kafka와 직접 통신할 수 있는 Kafka 테이블 엔진과 실시간 트리거 역할을 하는 Materialized View를 내장하고 있다. 이를 활용하면 추가 플러그인 없이 순수 SQL만으로 고성능 적재 파이프라인을 구축할 수 있다.

2. 2일 차 아키텍처 및 데이터 흐름

ClickHouse 내부에서는 데이터가 3단계 파이프라인을 거쳐 영구 저장된다.

[Kafka Topic] ──(Pull)──▶ [1. orders_kafka (Kafka Engine)]
                                  │
                         (실시간 트리거 감지)
                                  ▼
                       [2. orders_mv (Materialized View)]
                                  │
                           (JSON 파싱 및 적재)
                                  ▼
                       [3. orders (ReplacingMergeTree)]

  1. orders_kafka (Kafka 엔진 테이블): Kafka 브로커와 연결되어 메시지를 읽어오는 스트림 파이프 역할. 데이터를 영구 저장하지 않고 통과시킨다.

  2. orders_mv (Materialized View): orders_kafka에 새 데이터가 유입되는 즉시 감지하여 JSON 필드를 추출하고 타겟 테이블로 밀어 넣는 배관 역할.

  3. orders (ReplacingMergeTree 테이블): 실제 분석 쿼리가 수행되는 최종 영구 저장소.

3. ClickHouse 실시간 적재 파이프라인 구축 (SQL)

ClickHouse 컨테이너 CLI에 접속하여 3단 연동 테이블을 생성한다.

docker exec -it cdc-clickhouse clickhouse-client --user admin --password password

Step 1. Kafka 스트림 수신용 테이블 생성

1일 차에 Debezium 설정에서 VALUE_CONVERTER_SCHEMAS_ENABLE: "false"로 지정했기 때문에, 메시지 최상단의 before, after, op, ts_ms 키만 깔끔하게 수신할 수 있다.

CREATE TABLE orders_kafka (
    before Nullable(String),
    after Nullable(String),
    op String,
    ts_ms UInt64
) ENGINE = Kafka
SETTINGS
    kafka_broker_list = 'kafka:29092',
    kafka_topic_list = 'dbserver1.public.orders',
    kafka_group_name = 'clickhouse_orders_consumer',
    kafka_format = 'JSONEachRow';

Step 2. 최종 분석용 영구 테이블 생성 (ReplacingMergeTree)

열 지향 DB인 ClickHouse는 대량 삽입(Append-only)에 최적화되어 있어 일반 RDBMS처럼 행 단위 UPDATE를 직접 수행하지 않는다. 대신 CDC에서 들어온 변경 이력을 모두 쌓은 뒤, **ReplacingMergeTree(ts_ms) 엔진을 사용해 동일한 정렬 키(order_id) 중 가장 최신 타임스탬프(ts_ms)를 가진 행만 남기고 백그라운드에서 병합(Merge)**하는 전략을 사용한다.

CREATE TABLE orders (
    order_id Int32,
    user_id Int32,
    product_name String,
    amount Int32,
    status String,
    updated_at String,
    is_deleted UInt8,
    ts_ms UInt64
) ENGINE = ReplacingMergeTree(ts_ms)
ORDER BY order_id;

Step 3. 실시간 적재용 Materialized View 생성

Debezium의 작업 유형(op)에 따라 파싱 대상을 분기한다.

  • r(초기 스냅샷), c(INSERT), u(UPDATE): 변경 후 데이터인 after JSON 객체에서 값을 추출한다.

  • d(DELETE): after가 null이므로 삭제 전 데이터인 before 객체에서 order_id를 추출하고, 논리적 삭제 플래그(is_deleted = 1)를 기록한다.

CREATE MATERIALIZED VIEW orders_mv TO orders AS
SELECT
    JSONExtractInt(if(op = 'd', before, after), 'order_id') AS order_id,
    JSONExtractInt(if(op = 'd', before, after), 'user_id') AS user_id,
    JSONExtractString(if(op = 'd', before, after), 'product_name') AS product_name,
    JSONExtractInt(if(op = 'd', before, after), 'amount') AS amount,
    JSONExtractString(if(op = 'd', before, after), 'status') AS status,
    JSONExtractString(if(op = 'd', before, after), 'updated_at') AS updated_at,
    if(op = 'd', 1, 0) AS is_deleted,
    ts_ms
FROM orders_kafka
WHERE op IN ('c', 'r', 'u', 'd');

4. 실시간 정합성 검증 (INSERT / UPDATE / DELETE)

orders_mv 생성 직후 Kafka 토픽에 대기 중이던 초기 데이터가 자동으로 적재된다. 이제 운영 DB(PostgreSQL)에서 삽입, 수정, 삭제를 동시에 실행하여 ClickHouse에 정확히 반영되는지 검증한다.

docker exec -it cdc-postgres psql -U admin -d shop -c "
INSERT INTO orders (user_id, product_name, amount, status) VALUES (103, 'Monitor', 350000, 'PAID');
UPDATE orders SET amount = 140000 WHERE order_id = 1;
DELETE FROM orders WHERE order_id = 2;
"

1~2초 후 ClickHouse에서 데이터를 조회한다. 이때 백그라운드 병합이 완료되기 전이라도 중복 제거된 최신 상태만 조회하기 위해 FINAL 키워드를 사용한다.

docker exec -it cdc-clickhouse clickhouse-client --user admin --password password -q \
"SELECT order_id, product_name, amount, status, is_deleted FROM orders FINAL WHERE is_deleted = 0 ORDER BY order_id;"

검증 결과

  • order_id = 1: 기존 금액(150,000)이 수정된 금액(140000)으로 정확히 갱신됨

  • order_id = 2: 삭제(is_deleted = 1) 처리되어 유효 데이터 조회에서 제외됨

  • order_id = 3: 신규 삽입된 'Monitor' 데이터가 즉시 조회됨

5. 심화 실험: 내결함성(장애 복구) 및 성능 검증

파이프라인 구축을 넘어 실무에서 핵심이 되는 두 가지 시나리오를 추가로 검증했다.

1) 장애 격리 및 자동 복구 테스트 (Fault Tolerance)

ClickHouse 컨테이너를 강제로 중지(docker stop cdc-clickhouse)한 상태에서 PostgreSQL에 신규 주문 데이터를 삽입한 뒤, 다시 ClickHouse를 기동(docker start cdc-clickhouse)했다.

  • 결과: 분석계 DB가 다운된 동안에도 운영 DB(PostgreSQL)는 아무런 영향 없이 정상 동작했으며, 변경 이벤트는 Kafka 토픽에 안전하게 버퍼링되었다. ClickHouse 재기동 즉시 컨슈머 그룹 오프셋(clickhouse_orders_consumer)을 기반으로 밀린 데이터를 유실 없이 자동 적재하는 것을 확인했다.

2) OLTP vs OLAP 대용량 집계 성능 비교

PostgreSQL의 generate_series 함수를 이용해 더미 주문 데이터 50만 건을 일괄 생성한 뒤, 상품별 주문 건수와 매출 합계를 구하는 집계 쿼리(GROUP BY product_name)의 실행 속도를 비교했다.

-- PostgreSQL 더미 데이터 50만 건 삽입 예시
INSERT INTO orders (user_id, product_name, amount, status)
SELECT
    (random() * 1000)::int,
    (ARRAY['Mechanical Keyboard', 'Wireless Mouse', 'Monitor', 'USB-C Hub'])[floor(random() * 4 + 1)],
    (random() * 300000 + 10000)::int,
    'PAID'
FROM generate_series(1, 500000);
  • 분석: 행 지향 구조인 PostgreSQL은 전체 레코드를 순차 스캔해야 하는 반면, 열 지향 구조인 ClickHouse는 집계에 필요한 product_name과 amount 컬럼만 압축된 상태로 읽어 들여 수십 배 빠른 응답 속도를 보였다.

6. 전체 실습 회고

이틀간의 실습을 통해 데이터 엔지니어링의 핵심 개념을 직접 구현하고 체득할 수 있었다.

  1. 스토리지 아키텍처의 이해: 논리적 테이블은 동일하더라도 물리적 저장 방식(Row vs Column)에 따라 트랜잭션 처리와 대용량 집계 성능이 극명하게 갈린다는 점을 수치로 확인했다.

  2. CDC 기반 시스템 분리: 운영 DB에 부하를 주지 않고 WAL 로그만으로 데이터를 추출하고, Kafka를 완충 지대로 두어 분석계 장애가 운영계로 전파되지 않는 안정적인 아키텍처를 설계했다.

  3. ClickHouse 데이터 정합성 처리: Append-only 특성을 가진 열 지향 DB에서 ReplacingMergeTree와 FINAL, 논리 삭제 플래그(is_deleted)를 조합해 RDBMS의 변경 이력을 정합성 있게 동기화하는 실무 패턴을 익혔다.
