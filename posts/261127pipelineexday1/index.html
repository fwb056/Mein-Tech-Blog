[Data Engineering] 로컬 Docker로 실시간 CDC 파이프라인 구축하기 (1일 차: PostgreSQL → Debezium → Kafka)

2026-11-26

1. 들어가며: 왜 실시간 CDC 파이프라인이 필요한가?

서비스가 성장함에 따라 운영 환경의 트랜잭션 데이터(OLTP)를 실시간에 가깝게 분석용 데이터 웨어하우스(OLAP)로 이관해야 하는 요구사항이 발생한다.

  • 행 지향 DB (PostgreSQL, MySQL): 레코드 단위로 디스크에 연속 저장되어 단건 삽입·수정·삭제(OLTP)에 최적화되어 있다. 하지만 대용량 데이터 집계(GROUP BY, SUM) 쿼리를 직접 수행할 경우 전체 행을 스캔해야 하므로 운영 서비스에 심각한 부하를 유발한다.
  • 열 지향 DB (ClickHouse, BigQuery, Snowflake): 컬럼 단위로 연속 저장되어 대용량 집계 연산과 데이터 압축에 압도적인 성능을 발휘한다.

실무에서는 운영 DB의 부하를 격리하고 각 시스템을 독립적으로 확장하기 위해 운영 DB의 트랜잭션 로그(WAL)를 실시간으로 감지하여 메시지 브로커(Kafka)를 거쳐 분석계 DB로 적재하는 CDC(Change Data Capture) 파이프라인을 표준 아키텍처로 채택한다.

이번 실습은 별도의 애플리케이션 코딩 없이 Docker, 설정 파일, SQL만을 활용해 로컬 환경에서 PostgreSQL → Debezium → Kafka → ClickHouse로 이어지는 실시간 데이터 파이프라인을 구축하는 것을 목표로 한다.

2. 1일 차 아키텍처 및 작업 흐름

1일 차에는 원천 DB(Source)에서 발생한 데이터 변경 이벤트를 감지해 Kafka 토픽까지 안전하게 스트리밍하는 구간을 구축한다.

[PostgreSQL (OLTP)] ──(WAL Log)──▶ [Debezium Connect] ──(JSON Event)──▶ [Kafka (KRaft)] ◀── [Kafka UI]

핵심 구성 요소

  1. PostgreSQL 15: 운영 DB 역할. wal_level=logical 설정을 통해 논리적 복제 로그를 외부로 노출한다.
  2. Apache Kafka (KRaft 모드): 대용량 변경 이벤트를 버퍼링하고 목적지로 전달하는 스트리밍 플랫폼. 리소스 경량화를 위해 Zookeeper 없이 동작하는 KRaft 모드로 구성했다.
  3. Debezium Connect 2.6: Kafka Connect 위에서 동작하는 Source 커넥터. PostgreSQL의 WAL(Write-Ahead Log)을 읽어 DB에 쿼리 부하를 주지 않고 변경 내역을 실시간으로 캡처한다.
  4. Kafka UI: 토픽 생성 여부 및 적재된 JSON 메시지를 웹 브라우저에서 시각적으로 검증하기 위한 모니터링 도구.

3. 인프라 구성 (docker-compose.yml)

프로젝트 디렉터리를 생성한 뒤 전체 컨테이너 인프라를 정의한다. 추후 2일 차에 연동할 ClickHouse 컨테이너도 함께 정의해 두었다.

mkdir cdc-pipeline && cd cdc-pipeline

services:
  postgres:
    image: postgres:15
    container_name: cdc-postgres
    ports:
      - "5432:5432"
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: password
      POSTGRES_DB: shop
    command:
      - "postgres"
      - "-c"
      - "wal_level=logical" # Debezium CDC를 위한 필수 설정

  kafka:
    image: confluentinc/cp-kafka:7.6.0
    container_name: cdc-kafka
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: 'broker,controller'
      KAFKA_CONTROLLER_QUORUM_VOTERS: '1@kafka:29093'
      KAFKA_LISTENERS: 'PLAINTEXT://kafka:29092,CONTROLLER://kafka:29093,PLAINTEXT_HOST://0.0.0.0:9092'
      KAFKA_ADVERTISED_LISTENERS: 'PLAINTEXT://kafka:29092,PLAINTEXT_HOST://localhost:9092'
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: 'CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT'
      KAFKA_CONTROLLER_LISTENER_NAMES: 'CONTROLLER'
      KAFKA_INTER_BROKER_LISTENER_NAME: 'PLAINTEXT'
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      CLUSTER_ID: 'MkU3OEVBNTcwNTJENDM2Qk'

  kafka-ui:
    image: provectuslabs/kafka-ui:latest
    container_name: cdc-kafka-ui
    ports:
      - "8080:8080"
    environment:
      KAFKA_CLUSTERS_0_NAME: local-cluster
      KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:29092
    depends_on:
      - kafka

  debezium:
    image: quay.io/debezium/connect:2.6
    container_name: cdc-debezium
    ports:
      - "8083:8083"
    environment:
      BOOTSTRAP_SERVERS: kafka:29092
      GROUP_ID: 1
      CONFIG_STORAGE_TOPIC: my_connect_configs
      OFFSET_STORAGE_TOPIC: my_connect_offsets
      STATUS_STORAGE_TOPIC: my_connect_statuses
      KEY_CONVERTER: org.apache.kafka.connect.json.JsonConverter
      VALUE_CONVERTER: org.apache.kafka.connect.json.JsonConverter
      KEY_CONVERTER_SCHEMAS_ENABLE: "false"   # ClickHouse JSON 파싱 편의를 위해 스키마 메타데이터 제외
      VALUE_CONVERTER_SCHEMAS_ENABLE: "false"
    depends_on:
      - kafka
      - postgres

  clickhouse:
    image: clickhouse/clickhouse-server:24.3
    container_name: cdc-clickhouse
    ports:
      - "8123:8123"
      - "9000:9000"
    environment:
      CLICKHOUSE_DB: default
      CLICKHOUSE_USER: admin
      CLICKHOUSE_PASSWORD: password
    ulimits:
      nofile:
        soft: 262144
        hard: 262144

컨테이너 기동 및 상태 확인

# 백그라운드 실행
docker compose up -d

# 컨테이너 상태 및 Debezium REST API 준비 확인
docker compose ps
curl -s http://localhost:8083/connectors

4. 단계별 구축 및 검증 과정

Step 1. PostgreSQL 샘플 테이블 생성 및 복제 설정

PostgreSQL 컨테이너에 접속하여 주문(orders) 테이블을 생성한다. 이때 UPDATE나 DELETE 발생 시 변경 전 레코드(before)의 모든 컬럼 정보를 로그에 남기기 위해 REPLICA IDENTITY FULL 옵션을 반드시 설정해야 한다.

docker exec -it cdc-postgres psql -U admin -d shop

CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    amount INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 변경 로그에 전체 컬럼 정보를 기록하도록 설정
ALTER TABLE orders REPLICA IDENTITY FULL;

-- 초기 테스트 데이터 삽입
INSERT INTO orders (user_id, product_name, amount, status) VALUES
(101, 'Mechanical Keyboard', 150000, 'PAID'),
(102, 'Wireless Mouse', 80000, 'PAID');

Step 2. Debezium Source 커넥터 등록

Debezium REST API(8083 포트)에 POST 요청을 보내 public.orders 테이블의 변경 사항을 감지하는 커넥터를 등록한다. PostgreSQL 10 이상에서 기본 내장된 논리적 디코딩 플러그인인 pgoutput을 사용했다.

curl -i -X POST -H "Accept:application/json" -H "Content-Type:application/json" \
  http://localhost:8083/connectors/ -d '{
  "name": "postgres-orders-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "admin",
    "database.password": "password",
    "database.dbname": "shop",
    "topic.prefix": "dbserver1",
    "table.include.list": "public.orders",
    "plugin.name": "pgoutput"
  }
}'

등록 후 상태 확인 API를 통해 커넥터와 태스크가 모두 RUNNING 상태인지 검증했다.

curl -s http://localhost:8083/connectors/postgres-orders-connector/status

Step 3. Kafka UI를 통한 실시간 이벤트 검증

웹 브라우저에서 http://localhost:8080에 접속하여 dbserver1.public.orders 토픽이 자동 생성된 것을 확인했다.

  1. 초기 스냅샷 적재 확인: 기존에 INSERT 했던 2건의 데이터가 "op": "r"(Read) 이벤트 형태로 적재되어 있음을 확인했다.
  2. 실시간 변경(UPDATE) 테스트: PostgreSQL에서 주문 상태를 수정하자마자 별도의 배치 작업 없이 Kafka 토픽에 새로운 메시지가 즉시 유입되었다.
docker exec -it cdc-postgres psql -U admin -d shop -c \
  "UPDATE orders SET status = 'SHIPPED' WHERE order_id = 1;"

Kafka UI에서 확인한 UPDATE 이벤트 메시지에는 변경 전 데이터(before), 변경 후 데이터(after), 그리고 작업 유형을 나타내는 "op": "u" 필드가 정확히 기록되어 있었다.

5. 1일 차 회고 및 다음 단계

  • 핵심 배운 점:
    • KEY/VALUE_CONVERTER_SCHEMAS_ENABLE 옵션을 "false"로 설정하여 불필요한 스키마 메타데이터를 제거함으로써, 이후 ClickHouse에서 JSON을 파싱할 때 구조를 단순화할 수 있도록 설계했다.
    • Source 커넥터(Debezium)가 DB 부하 없이 WAL 로그만으로 변경 이벤트를 추출해 Kafka 토픽으로 발행하는 전체 메커니즘을 직접 검증했다.
  • 2일 차 목표:
    • 별도의 Sink 커넥터 플러그인 대신 **ClickHouse 내장 Kafka 엔진과 Materialized View**를 활용해 토픽 데이터를 실시간으로 적재한다.
    • ReplacingMergeTree 엔진을 적용해 UPDATE와 DELETE 이벤트의 최종 데이터 정합성을 보장하고, 대용량 더미 데이터를 통해 OLTP(PostgreSQL)와 OLAP(ClickHouse)의 집계 성능을 정량적으로 비교해 볼 예정이다.
