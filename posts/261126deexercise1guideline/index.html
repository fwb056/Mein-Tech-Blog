📊 데이터 저장 방식 및 실시간 CDC 파이프라인 정리 노트

1. 행 지향(Row-oriented) vs 열 지향(Column-oriented)

둘 다 논리적인 테이블 구조(RDB)는 동일하나, 디스크에 물리적으로 데이터를 연속 배치하는 기준이 다르다.

비교 항목 행 지향 (Row-oriented) 열 지향 (Column-oriented)
물리 저장 방식 한 행(레코드)의 데이터를 나란히 저장 같은 열(컬럼)의 데이터를 묶어 연속 저장
주 용도 OLTP (실시간 서비스 트랜잭션) OLAP (대규모 데이터 분석 및 집계)
쓰기·수정·삭제 빠름 (한 레코드 단위로 입출력) 느림 (여러 열 파일에 걸쳐 수정 발생)
특정 열 집계 조회 불필요한 열까지 읽어 I/O 낭비 발생 필요한 열만 골라 읽어 디스크 I/O 최소화
압축 효율 행마다 데이터 타입이 달라 낮음 동일 타입·유사 데이터가 모여 매우 높음
대표 기술/포맷 PostgreSQL, MySQL, Oracle ClickHouse, BigQuery, Snowflake, Parquet
  • 실무 표준 아키텍처: 서비스 운영 DB는 행 지향으로 구축하고, 이를 추출·변환(ETL/ELT)하여 열 지향 기반의 데이터 웨어하우스(DW)나 데이터 마트(DM)에 적재해 분석한다.

2. HTAP vs 실시간 파이프라인 분리

① HTAP (Hybrid Transactional/Analytical Processing)

  • 개념: 하나의 DB 엔진에서 행 지향(OLTP)과 열 지향(OLAP) 스토리지를 함께 운영하며 실시간 동기화하는 방식 (예: TiDB, SingleStore, AlloyDB).
  • 장점: 데이터 이동(ETL) 없이 데이터가 쌓이는 즉시 실시간 분석 가능(Zero-ETL), 파이프라인 관리 공수 절감.
  • 단점 (트레이드오프): 고사양 인프라 및 라이선스 비용 증가, 분석 쿼리 폭주 시 운영 서비스까지 느려지는 리소스 경합 위험.

② 직접 실시간 파이프라인 구축 (실무 표준)

  • 개념: 운영 DB(행 지향)와 분석 DB(열 지향)를 물리적으로 분리하고, 실시간 스트리밍 도구로 데이터를 동기화.
  • 장점: 분석 작업이 운영 서비스 성능에 영향을 주지 않음(완벽한 격리), 트래픽이 몰리는 쪽만 독립적으로 확장 가능.

3. 실시간 CDC 파이프라인 핵심 도구

흐름도: PostgreSQL (운영 DB) ➔ Debezium (변경 감지) ➔ Kafka (전달 통로) ➔ ClickHouse (분석 마트)

  • Debezium (CDC - Change Data Capture)
    • DB에 무거운 조회 쿼리를 날리지 않고, DB가 자체 기록하는 **트랜잭션 로그(PostgreSQL의 WAL, MySQL의 Binlog)**만 읽어 변경 내역(INSERT, UPDATE, DELETE)을 실시간 추출한다.
  • Apache Kafka
    • 추출된 변경 이벤트를 임시 저장하고 전달하는 분산 메시지 스트리밍 플랫폼.
    • 역할: 트래픽 폭증 시 데이터를 안전하게 쌓아두는 완충(Buffer) 역할 및 하나의 데이터를 분석 DB·알림·검색 엔진 등 여러 곳으로 동시에 보내는 1:N 허브 역할.
